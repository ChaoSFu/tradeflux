# 涨停板块雷达 / Limit-Up Sector Radar

页面 `/limit-up-radar`，2026-08-25 上线。

回答的不是"今天有哪些股票涨停"，而是：**资金今天在哪些板块形成了集团进攻，
这个板块的核心是谁，老核心和今天的新涨停有没有形成共振。**
所以输出单位是板块，不是个股。它负责 `Market → Sector → Leader → Setup → Trade`
链条里 `Sector → Leader` 这一段。

---

## 1. 数据源：实际核实过的东财字段语义

开工时按需求指定的接口先做了真实请求核对，结论跟字段字面含义有两处重要出入，
**后续任何人改这块之前请先读完这一节**，不要再按字段名推测。

### 1.1 `RPT_PCHOT_LIMITLIST_HSDETIAL` 不能单独支撑这个功能

| 核实项 | 结论（2026-08-25 实盘） |
|---|---|
| `SSLIMITUP_TIME` 是首封还是终封 | **最终封板时间**。跟涨停池逐行比对：41/41 等于 `lbt`，**0 例**等于 `fbt` |
| 有没有封单额 | **没有** |
| 有没有首次涨停时间 | **没有** |
| 是不是涨停股全集 | **不是**。当天只有 48 行，实际涨停 65 只，漏 17 只（含 002821 凯莱英） |

所以它被降级为**可选的涨停原因补充**（当天 41/65 有原因），
**绝不用来判断"今天谁涨停了"**。

### 1.2 真正的主数据源：`push2ex/getTopicZTPool`

必须带 `ut` 参数（不带时 `data` 返回空对象）。字段：

| 字段 | 含义 | 备注 |
|---|---|---|
| `fbt` / `lbt` | 首次封板 / 最终封板时间 | HHMMSS **整数**，`92500`=09:25:00，**上午只有5位** |
| `fund` | 封单额（元） | |
| `zbc` | 当日炸板次数 | |
| `lbc` / `zttj` | 连板数 / `{days,ct}` 即"N日M板" | |
| `p` | 最新价 **×1000** | 002821=`172230`→172.23，跟独立核实的实盘收盘价一致 |
| `hs` | 换手率 % | 002821=5.37，跟腾讯行情 `turnover_rate` 完全一致（交叉验证过） |
| `ltsz` | 流通市值（元） | 留给以后算封单占比 |

另接 `getTopicZBPool`（炸板池）算封板率 = 涨停/(涨停+炸板)。

### 1.3 降级策略

涨停池失败 → 抛错（没有涨停名单这个功能没意义）；炸板池/涨停原因失败 → 只记
warning，其余照常返回。**所有拿不到的字段一律 `None`，不用 0 或空串冒充"已知"**
——封单额为 0（无人排队）和"东财没给封单额"是两回事，页面分别显示 `0.00亿` 和 `—`。

## 2. 数据模型：为什么不塞进 StockDailySnapshot

| 表 | 唯一键 | 内容 |
|---|---|---|
| `limit_up_daily_details` | `(stock_id, trade_date)` | 涨停事件事实 |
| `broken_board_daily_details` | `(stock_id, trade_date)` | 炸板事实，只用来算封板率 |

`StockDailySnapshot` 是**日级状态与滚动窗口指标**（由K线窗口算出，语义是"这一天
收盘后这只股票是什么状态"）。涨停明细是**事件事实**（谁先封的、封了几次、排队
多少钱），来自完全不同的外部接口，而且**有明显日内时效**——用户可能 10:00、
13:30、14:50 各刷一次，封单额和最终封板时间每次都变。
混在一张表里会让"这一行是收盘定论还是盘中快照"无法区分。

炸板单独一张表而不是在涨停表加标志位：炸板股当天**没有**涨停，塞进去会让
"这张表里的行 = 当天涨停股"这个最基本的语义失效，之后每处聚合都要记得排除。

## 3. Core Recall：这个功能最重要的设计取舍

### 3.1 Core Recall ≠ Core Classification

召回条件是**宽 OR**，满足任意一条即进入核心区视野：

```
今日涨停 OR 近10日涨停≥2 OR 近20日涨停≥3 OR 近60日涨停≥5
OR 近60日最高连板≥3 OR is_leader OR is_core
OR in_strong_pool（强势股池成员，见 3.5）
```

阈值集中在 `limit_up_radar_service.py` 顶部常量，可用查询参数覆盖。

**这组条件只负责"把可能是核心的股票捞进视野"，不负责宣布谁是龙头。**
捞进来只打可解释标签（"近60日涨停7次"/"板块龙头"），不算综合分、不排名次。

### 3.2 为什么必须包含长窗口

一只经历过完整一轮行情的核心，进入震荡后可能近10日一次涨停都没有、今天只有 +2%。
只看今日涨停它消失，只看近10日涨停它还是消失。但它可能仍然是这个板块市场辨识度
最高的情绪锚。

它一旦从页面消失，用户看到"低位2只首板"就可能把
**「老核心负反馈 + 低位补涨」误读成「板块正在增强」**——这是完全相反的两件事，
也是这个功能最不能接受的失败模式。所以：

> 漏掉真正的核心，比同一只股票出现在两个板块严重得多。

默认 `all_watched_sectors`（一股可进多个关注板块，同板块内只出现一次），
另有 `primary` 模式给需要去重的场景。

### 3.3 ⚠️ 已修复的真实 bug：不能读 `Stock.limit_up_days_*`

**2026-08-25 用户在生产上发现，这是本功能上线后的第一个真实 bug，务必不要改回去。**

页面显示 002432 九安医疗「近10日涨停2次 · 近20日涨停5次 · 近60日涨停9次」，
拉真实K线数出来是 **0 / 1 / 7**。

**根因**：`Stock.limit_up_days_10d/20d/60d` 和 `board_count_60d` 只在 `daily_update`
处理**候选池内**股票时才重算（强势池 ∪ 涨跌停 ∪ 成交额前列）。九安医疗最后一次
涨停是 2026-07-31，之后掉出候选池，这几个字段就**冻结**在7月31日那天算出来的值，
一冻17个交易日。核对得上：截至07-31往前10日恰好2次、20日恰好5次、快照里全部涨停
日恰好9个。

**为什么对这个功能格外致命**：冻结值永远是"股票最热的时候"算的，必然偏高；
而 Core Recall 恰恰是设计来捞**已经冷却的老核心**——最需要它准的那批股票，
正好是它最不准的那批。结果是过度召回（实测 医药生物 核心锚从 32 只降到 13 只），
而且展示给用户的"召回理由"是一句**关于市场的假陈述**。

**修复**：`compute_limit_up_history()` 从 `stock_daily_snapshots` + 
`limit_up_daily_details` **现算**，不读 Stock 上的字段。
可靠性依据：非ST股只要当天涨停，就一定会被涨跌停选股API捞进候选池、一定会写当日
快照，所以"某天没有快照"⇒"那天没涨停"，缺失本身就是有效信息。

**这类 bug 的通用教训**：

> 任何"看起来是当前状态"的持久化字段，都要先问一句
> **"它是谁、在什么条件下写的？不满足那个条件时它会变成什么？"**
> `Stock` 上的滚动指标只对候选池内股票有效，池外的是历史残留值。

### 3.4 东财条件选股是滚动统计的**权威口径**（`CORE_RECALL_KEYWORD`）

数据来源优先级：**东财条件选股 > 本地快照重算 > `Stock` 冻结字段**。

选股接口每条结果都带活跃度字段（字段名含动态日期区间，**必须按前缀+窗口天数匹配，
不能写死完整键名**）：

```
DURATION_LIMIT_UP{2026-08-12|2026-08-25|10|天}  = 1     近10日
DURATION_LIMIT_UP{2026-07-29|2026-08-25|20|天}  = 6     近20日
DURATION_LIMIT_UP{2026-06-02|2026-08-25|60|天}  = 13    近60日
区间最高连板[2026-06-02至2026-08-25]             = 9.00  近60日最高连板
CHG / TURNOVER_RATE / NEWEST_PRICE                      今日涨跌幅/换手率/现价
```

> **踩过的坑**：一开始以为"次数拿不到"，因为 `fetch_strong_pool_codes(with_detail=True)`
> 的解析器是涨跌停专用的，只挑了 name/limit_dir/limit_date 三个字段就把其余全丢了。
> 结论是看了**我们自己解析器的输出**得出的，不是原始 payload。改代码前先 dump 原始
> 响应。

**为什么它比本地重算权威**：本地是从 `stock_daily_snapshots` 数涨停日，而快照只在
股票进候选池那天才写，历史有缺口就会数少。生产实测10只核心股覆盖率 **94.3%**，
600664 哈药股份近60日真实9次、快照里只有6次（漏了 07-10/13/14）。数少 ⇒ 漏召回。
东财是服务端实时算的，不依赖我们的历史完整性——2026-08-25 用 002432/600664/002437
跟真实K线逐项核对，**三只全对**。

**顺带解决**：`CHG` 给出今日涨跌幅，核心锚大多不在候选池、盘中没有当日快照，
"老核心正/负反馈"此前在盘中完全拿不到；接入后实测覆盖率从 4/17 提升到 25/25。

结果按交易日以 JSON 存进 `AppConfig`（key 前缀 `limit_up_radar:core_recall:`）。

#### ⚠️ 东财数的是"曾触及涨停"，不是"收盘涨停"

`DURATION_LIMIT_UP` **含炸板**。2026-08-25 用 603580 艾艾精工核实：
近60日收盘涨停 15 天 + 盘中触板未封 4 天 = 19，东财正好报 19。

用它做**召回**没问题（更宽 ⇒ 召回更全，符合第一原则），但显示成"近60日涨停19次"
会被读成19次收盘涨停。所以文案跟着来源走：

| 来源 | 指标 | 文案 |
|---|---|---|
| 东财 | 曾触及涨停（含炸板） | `近60日曾涨停19次（含炸板）` |
| 本地快照重算 | 收盘涨停 | `近60日涨停6次` |

### 3.5 强势股池成员无条件召回

强势股池（`STRONG_POOL_KEYWORD`）本身就是"选龙头"用的，两者**不合并 prompt**：

| | 强势股池 | 核心召回 |
|---|---|---|
| 范围 | **主板**非ST、非新股次新 | 非ST（含创业板/科创板/北交所） |
| 松紧 | 严（60日≥10次 / 10日≥5次 / 最高连板≥4） | 宽（60日≥5次 / 10日≥2次 / 最高连板≥3） |
| 进池代价 | 每天算K线/评分/写快照，重资源对象 | 板块卡上多一行 |

合并只能二选一：用严阈值会漏核心，用宽阈值会让强势股池膨胀好几倍。而且雷达的
板块里有大量创业板/科创板股，主板-only 的 prompt 直接覆盖不到。

包含关系改用**本地条件**保证：`recall_core_roles` 里 `stock.in_strong_pool` 直接算
一条召回理由。强势股池 prompt 怎么改，核心召回都自动覆盖它——不需要在两个自然语言
prompt 之间维护同步，那才是真正会漂移的地方。（强势股池 prompt 里"近20个交易日涨幅
前10"是纯趋势不含涨停，按涨停次数的条件本来就覆盖不到。）

## 4. 板块入选门槛与排序

### 4.1 入选门槛（AND，2026-08-25 新增）

`涨停只数 ≥ 3` **且** `最高连板 ≥ 3`，两个都不满足才留下。默认值可用查询参数
`min_limit_up` / `min_board_height` 调整。

生产上有 180+ 个板块当天有涨停，绝大多数是"涨停2只、最高1板"的噪音（互联网金融/
零售概念/生物疫苗这类），铺在页面上会把真正在形成集团进攻的板块淹掉。实测
182 → 6 个。

**这是 AND，代价要清楚**：涨停多但全是首板（基础化工涨停7/最高1板、建筑装饰6、
通信技术6）也会被滤掉。这是用户明确要的取舍——首板扎堆更可能是普涨或题材扩散，
有高板才说明有资金愿意接力，页面要回答的是"当前最强的板块和可能成为最强的板块"。

被滤掉的数量通过 `hidden_sector_count` 返回并显示在页面上（"已隐藏 N 个不达标
板块"），**不能悄悄丢**——用户得能看出是不是把想看的板块也滤掉了。全部板块都不
达标时，空态文案说明"今天没有形成有高度的板块进攻，这本身就是一个市场判断，
不是数据缺失"。

### 4.2 排序：全部词典序，不做加权总分

| 层级 | 排序 |
|---|---|
| 板块 | **最高连板 ↓** → 今日涨停数 ↓ → 连板股数 ↓ → 最早首封 ↑ → 总封单额 ↓ |
| 今日涨停股 | 连板数 ↓ → 首封时间 ↑ → 最终封板时间 ↑ → 封单额 ↓ → 近10日涨停 ↓ |
| 核心锚 | 板块标记 → 近60日 ↓ → 近20日 ↓ → 60日最高连板 ↓ → leader_score ↓ |

板块排序是**高度优先**（2026-08-25 从"涨停数优先"改过来）：连板高度是板块情绪
级别的直接体现，一个出了5板龙头的板块即使只有5只涨停，也比10只清一色首板的板块
更值得先看。

刻意不做 `0.4×涨停数 + 0.3×板高 + …` 这种加权总分：用户需要能一眼说清"为什么这个
板块排在前面"，加权分做不到。缺失时间排最后，不让 `None` 冒充"很早就封板"。

### 4.3 个股行展示的字段（列头可点击排序）

两张表的列头都可点击排序，交互沿用活跃股池：首次点一律降序，同列再点升降切换。
排序状态在所有板块卡之间共享——点一次，全部板块同步换序。

**缺失值永远排最后，与排序方向无关**：升序时让一堆 `—` 冒到最前面毫无意义，而且
会把"东财没给这个字段"看成"这只股票这项最低"。未选列时保持后端的业务排序
（连板→首封→终封→封单）。


两张表都带：涨停 10/20/60 日次数、60日最高连板、区间涨幅 10/20/60 日、龙头分、
风险分。全部走 3.4 的优先级链，**不直接读 `Stock` 上的冻结字段**。

- **区间涨幅**用东财 `INTERVAL_CHG`（真实复合区间收益）。注意它跟活跃股池那几列
  **不是同一个算法**：`compute_window_stats` 里的 `pct_change_Nd` 是"日涨幅简单
  相加"的近似，大涨股票严重低估——603580 艾艾精工近60日真实 204.85%，相加只有
  123.14%。两个页面的数字对不上是正常的，东财那个才对。
- **龙头分/风险分**是本仓库自己算的，只在 `daily_update` 处理候选池内股票时更新。
  核心锚大多在池外，那里的分数是冻结旧值。用 `scores_as_of_today`（该股今天有没有
  当日快照）判断本轮是否真的算过，没算过就返回 `None`、页面显示 `—`，不拿旧分数
  冒充当前。

## 5. 数据新鲜度：三份不同鲜度的数据必须分开表达

这个页面同时依赖三份新鲜度完全不同的数据，页面上分别显示，不能混成一个"更新时间"：

| 数据 | 怎么更新 | 页面显示 |
|---|---|---|
| 涨停/炸板明细 | 手动「刷新涨停数据」按钮，或 daily_update | `数据更新：HH:MM:SS` + 来源 |
| 近10/20/60日涨停次数 | 东财条件选股（刷新按钮/daily_update）；本地快照重算兜底 | `历史窗口算至：YYYY-MM-DD`（指本地兜底口径） |
| 核心锚今日涨跌幅 | 当日 StockDailySnapshot，缺失时用东财 CHG 兜底 | 覆盖率不足时不给正/负反馈结论 |

### 5.1 盘中"抛开今日"是刻意行为

交易日历是从 `stock_daily_snapshots` 的 distinct 日期反推的。盘中今天的
`daily_update` 还没跑 → 今天没有快照 → 窗口自然落在**截至上一个完整交易日**。
今天的涨停在"今日攻击"区单独展示，不混进历史窗口重复计算。落后1个交易日是盘中
常态，不告警；**落后≥2个交易日会告警**，因为那时"近10日"实际变成"截至N天前的
10日"，页面照样给出一个精确数字，但那个数字回答的不是用户以为的问题。

> 注意这跟 3.3 是同一类错误：**算得出来 ≠ 算的是对的问题**，而且都不报错。

**刻意不做的**：检测到过期就自动触发 `daily_update`。刷新按钮的范围是被需求明确
限定死的（见第6节），自动触发重活会破坏这个边界。做法是**检测 + 显式告知 + 告诉
用户去点「每日数据更新」**。

### 5.2 核心锚今日涨跌幅的覆盖率问题

核心锚的今日涨跌幅取自当日 `StockDailySnapshot`，而快照只覆盖候选池里的股票——
宽召回捞出来的核心锚大多不在候选池内，所以覆盖率天然偏低。生产实测出现过
**21只核心锚里只有1只有当日数据、均值 +5.42%** 的情况。

那1只代表不了整个板块老核心的状态，直接挂上"老核心正反馈"会把一个样本误读成
板块级判断，而这恰恰是本页面最重要的那个结论。所以：
**至少3只、且覆盖≥30% 才给正/负反馈结论**，不够就只给数字加"样本不足，不作判断"
和覆盖率。

## 6. 手动刷新的范围是硬边界

`POST /limit-up-radar/refresh` **启动后台任务并立即返回**（约 5ms），页面轮询
`GET /refresh/status` 直到 `running=false` 再刷新数据。任务本身做四件事：

1. 涨停池 + 炸板池 + 涨停原因 → upsert 两张明细表
2. 东财条件选股 → 核心召回名单（含涨停次数/区间涨幅/今日涨跌幅）
3. **为本页面上的股票重算龙头分/风险分**（2026-08-25新增，见下）
4. 结果写两张明细表 + 两个 AppConfig

### 6.0 ⚠️ 为什么必须是异步（2026-08-26 修的真实问题）

用户反馈"点了刷新，后台数据更新了但前端没刷新，等我点别的地方才出来"。

根因：加上第3步（重算龙头分/风险分）之后整个刷新实测 **37.8 秒**，而前端 axios
的全局超时是 **15 秒**——请求被前端掐断，`onSuccess` 不触发、`invalidateQueries`
不执行，但**后台线程其实已经把活干完了**。表现就是"点了没反应，过一会儿手动切换
才看到新数据"。

单纯调大超时不解决问题：让用户对着转圈等 40 秒本身就不对。改成跟弱转强雷达同一套
模式（后台线程 + 状态轮询），按钮上实时显示当前步骤（"东财条件选股（板块核心
召回）"/"重算本页股票龙头分/风险分"），跑完自动刷新数据。

**这不违反"不做自动轮询"**：那条约束针对的是"页面自己定时打外部接口"。这里是
用户主动点击后、为了拿到这一次的结果而轮询**本地状态接口**，拿到结果就停。

**绝不触发**：`daily_update`、全市场选股、Market State 重算、弱转强雷达刷新、
板块全量同步、AI点评。

### 6.1 龙头分/风险分为什么要在刷新时现算

这两个分数是本仓库用65日K线窗口自己算的（`compute_window_stats`），东财给不了。
而 `daily_update` 只对候选池内的股票重算——核心锚大多在池外，那里的分数是冻结
旧值（跟 3.3 的涨停次数是同一类问题）。

**范围严格限定在会显示的股票**：先按跟 `build_radar` 同一套门槛筛出达标板块，再取
这些板块的成员 ∪ 今日涨停股。不筛的话召回集会覆盖全部关注板块——实测 200 只 /
11 秒，筛完 101 只 / 5.8 秒，才对得起"快速刷新"的定位。

**结果不写进 `Stock`**，单独存页面作用域的 AppConfig（key 前缀
`limit_up_radar:scores:`）。这是刻意的：刷新有"不改动主流程数据"的硬保证，而且
盘中用半日K线算出来的分数写进 `Stock` 会污染强势池/板块情绪/龙头识别等一系列
下游消费者。**页面要的是"现在什么样"，主流程要的是"收盘定论"，不能共用一个字段。**

护栏测试相应调整了语义：`test_refresh_only_syncs_limit_up_details` 现在允许K线
拉取，但断言请求的股票数受限（≤200）；另有
`test_refresh_recomputes_scores_only_for_stocks_on_this_page` 断言 `Stock` 上的
分数纹丝不动。

**改刷新逻辑时不要绕过这两条测试。**

不做自动轮询，维持 manual-first——只在用户主动点击时打外部接口，避免不必要的
限流/封禁风险。

`daily_update` 里这一步用 try 包住，失败只记 warning 并 rollback，绝不影响已有的
K线/Stock/Sector 主链路；反向也有护栏
（`test_sync_never_touches_stock_scores_or_snapshots`）：这一步成功时也不能改动
主流程的数据。

## 9. K线数据源的兜底顺序（2026-08-26 修正）

```
候选轮询拆两组 ──┬─→ 腾讯（并发）
                 └─→ 新浪（并发）
                        ↓ 本组失败的
                 交叉兜底：分到腾讯的去试新浪，分到新浪的去试腾讯
                        ↓ 两个主力源都拿不到的
                 东财 push2his（单跳，不递归）
```

**东财早就不是主力**，push2/push2his 生产环境长期被针对性限流（`RemoteProtocolError`
成片），只留兜底角色。

### ⚠️ 腾讯有当日未完成bar，新浪没有

2026-08-26 实测（盘中 12:54）：

```
腾讯日K：66根，末根 2026-08-26   ← 盘中就发布当天那根未完成的bar
新浪日K：65根，末根 2026-08-25   ← 盘中不发布
东财：   RemoteProtocolError     ← 被限流
```

后果：盘中跑 daily_update 时，轮询分到新浪组的股票**无论重试多少次都拿不到当日
bar**——不是报错，是这个源就没有。生产日志 `90 只失败 → 重试补齐 45 → 45 只仍缺失`
的"每次恰好一半"完全是分组比例（181/2≈90，90/2=45），跟限流无关。

所以 `fetch_klines_batch` 有 `require_date` 参数：传入时，**"返回了数据但没有那一天
的bar"也算没拿到**，会触发交叉兜底。只按"结果为空"判断的话，新浪返回的65根非空
数据会被当成成功，交叉兜底压根不触发。实拉验证：12只股票，不传 6/12 拿到当日bar，
传了 12/12。

兜底结果**只在确实更好时才替换**，绝不 `update()` 一把覆盖——兜底源失败返回的是空
list，会把主力源拿到的"有效历史窗口、只是缺当日bar"整个抹掉，MA60/连板数/N日涨停
随之全部失真。（这个 bug 是上面那条回归测试当场抓出来的。）

交叉兜底那一层是 2026-08-26 补的。原来是"本组主力失败 → 直接跳东财"，但**另一个
主力源当时往往是好的**，只是恰好没被分到这只股票。生产日志实测：002078 分在腾讯组
→ 腾讯 `JSONDecodeError` → 直接撞东财 `RemoteProtocolError` → 失败，全程没试过新浪。
那一轮 169 只里有 106 只（63%）最后靠实时行情补当日 bar 救回来，代价是换手率缺失、
且只补得到今天这一根。

换手率只有东财K线有（腾讯/新浪都没这个字段），所以走主力源的股票换手率诚实缺失，
不编造——见 3.4 和 `KLineBar.turnover_rate` 的说明。
